Zivaa — Holistic Lab Report & Biomarker Reference
A build reference for the Zivaa lab-report feature. Organised by panel, with biomarkers, representative reference ranges, and interpretation logic (what makes a value good vs. flagged).
Clinical caveat: All ranges below are widely-used representative values and must be clinically validated by a physician on your team before they drive any flagging. Every real lab report prints its own reference range — parse and store that, don't hardcode these.
How to read this document
Each biomarker carries three things your rules engine needs:
Reference range — the "normal" band (lab- and demographic-dependent)
Direction of concern — whether high, low, or both is the problem
Clinical target override — where a member's condition changes the threshold (e.g. diabetic LDL target < 70, not < 100)
Flag tiers map to Zivaa's existing system: Green (in range) · Amber (borderline) · Red (critical → Guardian action).

PART H — INTERPRETATION LOGIC (the rules engine)
The core principle: "good vs. not good" is never a single hardcoded number. It's a function of five inputs.
1. Lab-provided range is source of truth
Every report prints its own reference band per marker (varies by equipment/method/population). Parse and store the printed range per result — don't rely on the tables above at flag-time.
2. Demographic adjustment
Ranges shift by age, sex, and pregnancy. Several markers (ESR, creatinine, testosterone, PSA) have age-dependent bands. Elderly ranges differ from general adult ranges.

4. Three-tier flagging → Zivaa Green/Amber/Red
Green — within the applicable range/target
Amber — borderline (prediabetic band, Vitamin D 20–30, mild enzyme rise)
Red — critical (K >6.5, glucose >300, troponin positive, Na <120) → triggers Guardian action
Maintain a critical-value table separate from normal ranges — these are the absolute thresholds that page a Guardian regardless of member context.
5. Trend over snapshot
A creatinine climbing 1.0 → 1.2 → 1.4 across three quarters is more meaningful than one borderline value. Treat every biomarker as a time series, not a point reading. This is the natural fit with Zivaa's Baseline model — surface "HbA1c crept 6.9 → 7.4 over two quarters" rather than a raw dump.
PART I — SUGGESTED DATA MODEL
LabReport
  ├─ id, member_id
  ├─ report_date, source_lab, panel_type
  ├─ raw_pdf_ref, ocr_confidence
  └─ BiomarkerResult[]
        ├─ biomarker_code, value, unit
        ├─ lab_provided_range_low / _high   ← source of truth
        ├─ member_specific_target           ← condition override
        ├─ status_flag (green/amber/red)
        └─ computed_at
Member
  └─ ConditionTarget[]
        ├─ condition (diabetic, cardiac, ckd, warfarin…)
        ├─ biomarker_code, target_low / _high
CriticalValueTable   ← global, condition-independent Red thresholds
        ├─ biomarker_code, critical_low / _high
Flag computation order
Is value past a critical threshold? → Red (page Guardian)
Does member have a condition-specific target? → flag against it
Else → flag against lab-provided range
In all cases → append to the biomarker's time series and compute trend
PART J — ENGINEERING NOTES FOR INDIAN LAB PDFs
The real challenge is parsing, not the ranges. Indian lab reports come in wildly inconsistent formats:
Major labs: Dr. Lal PathLabs, SRL Diagnostics, Metropolis, Thyrocare, Apollo, Vijaya, Agilus — each with its own PDF layout
Mixed units (mg/dL vs mmol/L), Hindi/English bilingual reports, scanned vs. digital PDFs
Panel names vary ("KFT" vs "RFT" vs "Renal Panel"; "SGPT" vs "ALT")
Recommendation: build a biomarker-synonym dictionary (map "SGPT", "ALT", "Alanine Transaminase" → one canonical code) and prototype the OCR/parser against real reports from the top 3–4 labs before committing to the flagging layer. The parser is where this feature succeeds or fails.
